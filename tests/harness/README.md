# tests/harness — the rendered checks

*Playwright, run against this corpus's own build, checking the site features of the theme-parity harness (QuantEcon/project-theme-parity#15, D9), every page for error markers, console errors and sideways scrolling, and on every page how many times the theme drew each construct family (D18); it writes `rendered.csv`, `counts.csv` and `provenance.json`, which CI publishes at `/_harness/`.*

Last updated: 2026-11-26

This is layer 3 of the parity harness, the mystmd side of QuantEcon/test-lecture-theme-mystmd#2. Its twin in QuantEcon/test-lecture-theme-sphinx checks the Sphinx site with the same engine and writes the same CSV, and QuantEcon/project-theme-parity folds the two files into a pass. The parity repository is private, so the checks live here, where this repository's CI can run them on the build it just made. They sit outside `lectures/`: `bin/sync-from-sphinx` writes only `lectures/`, and `sync-check` diffs only that, so the sync never touches them and they need no exclusion.

## Running it

```bash
cd tests/harness && npm ci && npx playwright install chromium
npm run selftest                                                              # the fixtures, below
node run.mjs --dir ../../lectures/_build/html --base-path /    # a site built with BASE_URL unset
node run.mjs --url https://quantecon.github.io/test-lecture-theme-mystmd/   # the live site
```

Both ways write `_harness/rendered.csv`, `_harness/counts.csv` and `_harness/provenance.json` at the repository root (`--out` to change it) and print the counts by check and result, then what `counts.csv` holds. A built site is served at the base it was built with. `myst build` bakes `BASE_URL` into the site: `ci.yml` sets it to `/test-lecture-theme-mystmd` on a push to `main` and leaves it empty on a pull request, so a push's build is served at `/test-lecture-theme-mystmd/` and a pull request's at `/`, and `provenance.json` records which. `run.mjs` stops (exit 2) when the build's home page asks for assets outside the base it was given. `--only id,id` runs those features alone, `--pages stem,stem` gives the page-wide checks those pages only (the behaviours still read the whole site's order), and `--no-pages` leaves out the page-wide checks, and so the drawn counts, which are taken in their page loads. `--drawn FILE` counts with another drawn table than `drawn.yml`, and `--no-drawn` takes no counts and writes no `counts.csv`.

The exit status: 0 when every check ran and every count was taken, whatever they found; 1 when a check could not run (an `error` row, which is still written) or a drawn selector threw (its counts are written empty); 2 when nothing was checked (a bad argument, a locator or drawn table that does not parse, a site that cannot be served or does not answer, or a build made for another base: its home page's canonical link, or an asset it asks for, puts it somewhere other than the base it was given).

## What it checks

- **Every site feature** in `locators.yml`, on the page and at the viewport its entry names, in light and dark. `present`: does the locator match? `behaviour`: where the entry names one, the behaviour is exercised (`theme.mjs` and `lib/behave.mjs`, keyed by the feature id). Each check gets a fresh browser context, so nothing one check writes to `localStorage` reaches another, and on the live sites, which share the origin `quantecon.github.io`, nothing one site writes reaches the other's checks.
- **Every page** at desktop (1280), tablet (820) and phone (390), light and dark: `error-marker` (`mjx-merror`, `.katex-error`, mystmd's red KaTeX message, MathJax's red undefined macro, mystmd's yellow message for inline maths that failed, maths left as raw TeX, the "… - Unknown Directive" title mystmd gives an unknown directive's box, `.system-message`, `.problematic`; mystmd renders an unknown role as its plain text, which no marker can see), `console` (console errors, hydration warnings and uncaught errors on load) and `overflow` (`scrollWidth` beyond `clientWidth`, so the page scrolls sideways).
- **Every construct family's drawn surfaces**, in those same page loads: how many times the theme drew each family that `drawn.yml` gives this site a selector (`counts.csv`, below).

**The colour scheme.** The theme takes its scheme from `@myst-theme/site`: on a static build it reads `localStorage` `myst:theme` first and, without one, follows `prefers-color-scheme` (`useTheme`, and the `BlockingThemeLoader` before hydration). Each context emulates the preference and leaves the key unset, as for a reader who has not chosen, and before any check runs, the harness confirms the scheme took effect (`html.dark` in dark, not in light); a page where it did not gives `error` rows. mystmd highlights code after hydration, so a page is read a second after network idle, once the document stops changing.

**The maths markers.** mystmd renders this site's maths with KaTeX at build, and the theme serves KaTeX's stylesheet itself, so no CDN can leave it unrendered. An undefined macro is a KaTeX parse error ("Undefined control sequence"): in display maths mystmd shows the red message, in a `<pre>` titled with it; in inline maths, myst-theme's `InlineError`, a yellow span titled with the message, which no marker read before. That span also marks a cross-reference or citation not found, so only a title in KaTeX's words ("at position N", "at end of input") counts as a maths error. TeX left with its delimiters (`$$…$$`, `\[…\]`, `\(…\)`, an environment) in the page's text, outside code and KaTeX's own output, is TeX the parser did not take as maths. A single `$…$` left in the text is not read, since a lone `$` is as often a price as maths, so inline maths the parser missed goes unseen. On the Sphinx site MathJax typesets in the browser: an undefined macro there is its name in red, and raw TeX in the elements MathJax is asked to typeset is maths MathJax never rendered, every expression when its CDN fails.

A check result is data: a failed feature check, a marker, a console message or an overflow is a row, not a failed job. So is a control a behaviour has to operate and cannot, because it is not shown or will not take the click: that is `fail`, with the control named, where a behaviour that throws for any other reason is `error`. Links are fetched from the browser's context, each URL once a run. A Downloads item that is no link (theme v3.2.1 draws each as a Radix menu item that fetches its file when selected) is selected instead, the menu opened again for each, and what it did is the evidence: the URL its fetch asked for and the name of the file it downloaded, with that URL's status fetched as a link's is (`download-notebook`, `download-pdf` and `notebook-header` read the menu so). A link that answers with a failure (a 404, say), or a target that names the wrong file, makes its check `fail`; only when nothing failed does a link that gets no answer (no connection, a 429 rate limit or a 5xx, after two more tries) leave the check `skip`, for a person. Each behaviour has one time budget, 100 s inside its 120 s limit, and its retries stop before the budget runs out, so a slow or rate-limiting host gives `skip`, not `error`. The checks that read the clipboard take turns, since the browser has one clipboard, and each puts a marker on it and reads it back before pressing, so a button that copies nothing cannot pass on text another check left there; when the marker is not there to read back (the write failed), nothing is pressed and the check is `skip`: the clipboard could not be primed, and a person checks it.

## rendered.csv

One row per check, with the columns of QuantEcon/project-theme-parity#15, the same in both corpora so their rows join:

| Column | Holds |
| --- | --- |
| `page` | the page's Sphinx name (`code_cells`, served here at `code-cells/`; `intro` at the base), on both sites |
| `family` | the feature id, or `page` for the page-wide checks |
| `check` | `present`, `behaviour`, `error-marker`, `console` or `overflow` |
| `viewport` | `desktop` (1280), `wide` (1440), `tablet` (820) or `phone` (390) |
| `scheme` | `light` or `dark` |
| `result` | one of the six below |
| `detail` | the evidence: a count, what the behaviour did, a message, a URL and what it answered |

| Result | Means |
| --- | --- |
| `pass` | the check ran and held |
| `fail` | the check ran and did not hold: a behaviour failed, or a marker, console message or overflow was found |
| `absent` | `present` only: the locator matched nothing |
| `none` | no locator: this site has no counterpart (`null` in the table), on `present` and `behaviour` |
| `skip` | the check ran but could not decide; `detail` says why, and what a person has to look at instead |
| `error` | the check could not run: it threw, the page did not load, or the colour scheme did not take effect |

`present` counts every part of a locator, as `<matched> (<visible> visible)`, and the first part decides `pass` or `absent`: the locator matching, as the parity harness's rule reads it. Whether the match is shown is in the detail, not the result, since a head element (the canonical link, the favicon, `rel="prev"`) is never shown and some controls show only on hover or scroll; a control a behaviour needs and cannot find shown fails that behaviour. The rows come in a fixed order: the features in the table's order (light, then dark; `present`, then `behaviour`), then the pages in the site's order (`lectures/myst.yml`).

## counts.csv

How many times this site's theme drew each construct family on each page: the drawn side of QuantEcon/project-theme-parity#15's drawn checks, by D18's route A. The counts know nothing of the engine. QuantEcon/project-theme-parity's `bin/measure` sets each one beside the same build's own engine count (`structure.csv`, from this build's page AST), never beside the other site's. They are taken in the page-wide checks' page loads, after the page has settled, its scheme has been checked and its error markers read, so the six readings cost no page loads of their own.

| Column | Holds |
| --- | --- |
| `page` | the page's Sphinx name, as in `rendered.csv` |
| `family` | the family id, expanded (`prf-theorem`, `heading-h2`), as in `drawn.yml` |
| `viewport` | `desktop` (1280), `tablet` (820) or `phone` (390): the page-wide checks' three |
| `scheme` | `light` or `dark` |
| `drawn` | how many elements the family's selector matches in the settled DOM, shown or not: the theme put the surface on the page. An integer of 0 or more; empty when the count could not be taken |
| `shown` | how many of those are visible on load, by the test `present` counts with (a non-empty box and no `visibility: hidden`), with nothing scrolled, hovered or opened: an integer from 0 to `drawn`, empty exactly when `drawn` is |

There is one row for every page, every family `drawn.yml` gives this site a selector, every viewport and every scheme, zeros included: 17 pages × 51 families × 6 readings = 5,202 rows here (on the Sphinx site, 16 × 53 × 6 = 5,088). A zero is a measurement and a missing row is an input error, so "the theme drew none" is never confused with "nobody counted". A family whose selector is null writes no rows, and `provenance.json` records it as not counted. The rows come in a fixed order: the pages in the site's order, then desktop, tablet, phone, then light, dark, then the families in the table's order. They join to `rendered.csv`'s page-wide rows on `page, viewport, scheme`.

A count is data, never a failed job: a 0 where the engine produced some is for the fold to find. `drawn` and `shown` are empty when the page did not load or its scheme did not take effect (that page's `error` rows in `rendered.csv` say which), or when the selector threw. A selector that throws is a harness fault: the run exits 1, as an `error` row makes it do, and `provenance.json` names each reading not taken. `shown` is below `drawn` where the theme folds a surface on load (what sits behind a `hide-*` toggle or inside a closed solution) or hides it. It is evidence, not a number to compare between the two sites, which fold differently. A family drawn a different number of times at two readings of one page is a finding in itself.

## provenance.json

The repository and commit (`commit` is the pull request's head on a pull request; `checkout` the commit checked out), the workflow run, what was read (a built directory and the base path it was served at, or a URL) and the commit its `build_info` page prints, the locator table's source commit and its corrections, the pages, the viewports, how each scheme was set, the Playwright and browser versions, Node, and the UTC start and finish. Schema 2 adds the drawn counts and `outputs`, the files written. `drawn` gives the table (`file`), its source commit and side (`copied_from`), its corrections, how many families it counts (`families`) and how many it does not, by `why` (`not_counted`), the rows of `counts.csv`, and each reading not taken (`uncounted`: page, viewport, scheme, the family or null for the whole page, and why). When no counts were taken (`--no-drawn` or `--no-pages`), `drawn` is null and `outputs` lists `rendered.csv` alone.

## The locator table

`locators.yml` is a copy of `bin/site-features.yml` in QuantEcon/project-theme-parity, each entry's `checks` and only this theme's side, at the commit its `source` names. Every locator was checked against this build before the copy; one that has moved on this site is corrected here, with a `corrected: {from, why}` note, and the correction is carried in `provenance.json`.

## The drawn table

`drawn.yml` is a copy of `bin/drawn.yml` in QuantEcon/project-theme-parity, written by that repository's `bin/copy-locators --table drawn mystmd <this checkout>`. It holds every family id of that repository's `bin/families.yml`, `each` expanded, with only this theme's selector, at the commit its `source` names. A selector is a Playwright selector, every element it matches counting, or `{select, in, text}`: the elements `select` matches whose own text, or the text of their first `in` descendant, whitespace collapsed and trimmed, matches the regular expression `text`. Where this theme draws no surface a selector can count, the selector is null, with a `why` (`invisible`, `inline-maths`, `report`, `styling`, `anchor`, `no-surface` or `text`). `lib/table.mjs` checks the table's shape before anything is checked. Every selector was checked against this build before the copy; one that has moved on this site is corrected here, with a `corrected: {from, why}` note, carried in `provenance.json`, until the list carries the correction.

## The self-test

`selftest/good/` and `selftest/bad/` are small static sites in this theme's markup, checked with `selftest/locators.yml` through the same engine and `theme.mjs`, their rows compared with `selftest/expected-*.csv`. Each is built twice, for `/test-lecture-theme-mystmd/` and for `/` (the base a pull request's build is made for): copied with every `{{base}}` replaced by the base, as a build writes its base into its canonical links, and served at that base, so `page-meta` and every other check that reads the base is read at both, against the same expected rows. Between them every check type passes and fails and every result appears: a working dark-mode toggle and a broken one, a stderr fold that works and one that does not, a copy button that copies the cell and one that copies nothing, a clipboard the harness cannot prime (the bad page refuses clipboard writes in dark, so its copy check is `skip`), a page whose canonical link, `og:url` and meta tags are right and one where they are not (in light the canonical link alone is wrong; in dark `og:url` names another page and `twitter:card` is missing), mystmd's red KaTeX message, an undefined macro in inline maths (the yellow message) and its "Unknown Directive" box title, a maths page with TeX the parser left raw and one where KaTeX rendered it, a console error and a hydration warning, a page wider than every viewport, a null locator, a locator that matches nothing, a check that cannot decide, a behaviour that throws (given a locator without the part it presses), a feature at the `wide` viewport, a missing page, and a page whose dark scheme does not take effect. Each site's `code_cells` page has a Downloads menu as theme v3.2.1 draws it, menu items with no link that fetch their file when selected: on the good site the book PDF and the page's notebook answer 200 (and `notebook-header` reads the notebook's first cell), on the bad site both fetches answer 404. Then `run.mjs` itself runs on each build of the good site, with `page-meta`: at the base the build was made for, its `page-meta` rows must pass, so `run.mjs`'s own reading of the base is checked and not only the self-test's copy of it; at the other base, its build-base check must stop it with exit 2. The drawn counts are taken in the same runs, with `selftest/drawn.yml` (six entries: four with this site's real selectors, a null family, and a selector the browser cannot parse), and compared with `selftest/expected-good-counts.csv` and `selftest/expected-bad-counts.csv` exactly, row for row and in order. They hold a cell shown and an output inside a closed fold (drawn 1, shown 0), a solution a style hides (drawn 1, shown 0), `solution`'s `{select, in, text}`, which keeps the solution's box and drops the exercise's (and the real selectors' refinements: the theme's id-less toolbar block in a cell and a cell's empty outputs container are not counted), pages where nothing matches (0), a null family (no rows), the selector that throws (empty), and the missing page and the page whose dark scheme does not take effect (empty). The expected counts are the same in both corpora. Then `run.mjs` counts the good site's `intro` with that table: it must write the same counts, record the selector that threw in `provenance.json`, and exit 1 for it alone; and its run without page-wide checks must write no `counts.csv`. CI runs the self-test before the real run; a mismatch fails the job, and in GitHub Actions each site's mismatches are also an `::error::` annotation on the run.

## Files

- `run.mjs` — the command; `theme.mjs` — this site's side: page addresses, the scheme, settling, its own behaviours
- `lib/` — the engine, the same in both corpora: `engine.mjs` (the run), `behave.mjs` (the behaviours both themes share), `markers.mjs`, `util.mjs`, `table.mjs` (reads and checks the two tables), `server.mjs` (a static server under a base path, after quantecon-theme.mystmd's `static-server.mjs`), `csv.mjs` (`rendered.csv` and `counts.csv`)
- `locators.yml`, `drawn.yml`, `selftest/`, `package.json` and `package-lock.json` (`@playwright/test` and `yaml`, pinned)

`.github/workflows/harness.yml` runs it after the build job of `ci.yml`, on every event, uploading `_harness/` as the run's `harness` artefact. The deploy job then uploads the Pages artefact with `_harness/` in it when the checks succeeded and without it when they did not, and on a push to `main` publishes it. A run cancelled while the checks ran uploads and publishes nothing. Its first step checks that the shared engine (`lib/`, `run.mjs`, `selftest/run.mjs`, the package files but for their names, and `harness.yml` itself) matches the twin corpus's: on a pull request, the twin's branch of the same name when there is one, else its `main`, and a difference fails the job; on a push it only warns, since one half of a two-corpus change always merges first. So a change to the engine is made in both corpora, on one branch name. The run's step summary, and a notice on the run, give what `counts.csv` holds: its rows, the families counted and not, any empty counts, any count that differs between a page's readings, and each family's totals at desktop in light, so CI's counts can be read without the artefact. A second notice, written by `theme.mjs` as `run.mjs` exits, lists the rows of the features it names (`NOTICE_FAMILIES`: today `download-notebook`, `download-pdf` and `notebook-header`), so CI's reading of them is on the run's annotations too.

The text-present check (not now, by D18: the two stacks number in different ways). Metrics and crops (for the visual layer, QuantEcon/project-theme-parity#8). Every feature at every viewport.
